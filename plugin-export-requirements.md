# Требования к выгрузке figma-design-ir: скоуп «только используемое»

Инструкция для агента, правящего экспорт-плагином Figma. Описывает, **каким должен быть результат выгрузки** (вход для consumer-скилла `figma-to-code`), на основе разобранного реального случая. Внутреннее устройство плагина не известно — всё формулируется через наблюдаемое поведение и структуру архива.

## 1. Проблема на реальном кейсе

Selection = один фрейм-попап `27053:15077` (500×820, страница «🟠 Design»). Ожидание — компактный архив с этим попапом. Факт:

| Метрика | Сейчас | Должно быть |
|---|---|---|
| Всего | **305 МБ, 5990 файлов** | < 30 МБ, < 800 файлов |
| `ir/components/definitions/` | 881 файл, 251 МБ | ~51 файл, < 10 МБ (или 0 — см. §3.2) |
| `assets/vector/` | 3326 SVG, 20 МБ | 8 SVG, ~7 КБ |
| `agent/components/` | 881 md, 13.5 МБ | ≈ числу включённых definitions |
| `raw/rest-v1/components/` | 881 файл, 2.1 МБ | зеркало used-набора (или 0) |

Диагностика: 701 warning / 185 error — в основном про недоступные библиотечные definitions, которые не нужны были вовсе.

### Механика раздувания

Плагин экспортирует **все варианты каждого затронутого component set'а**, а не только инстанцированные варианты. Расклад лишних definitions по сетам в этом кейсе:

- Флаги стран (сеты `20001:64`, `25002:14584`): 372 определения, 82 МБ — попап использует 2 (`russia`, `portugal`)
- Платёжные методы (сеты `20001:1450`, `25002:15970`): 269 определений, 142 МБ — использует 1 (`Mastercard sm`)
- Кнопки (сеты `25002:11420`, `27053:15043`): 162 определения, 19.6 МБ — использует ~12 конкретных вариантов

То же самое размножается в `assets/vector`, `agent/components`, `raw/rest-v1` и `component-index.md` (881 запись).

## 2. Ключевой факт, на котором держится вся оптимизация

`ir/nodes/roots/<root>.json` (`normalizedTree`) **уже полностью самодостаточен**: инстансы библиотечных компонентов инлайнены в дерево целиком (geometry, visual, text, instanceData), точные значения на месте. Доказательства:

- 30 top-level source-id'ов инстансов попапа **вообще отсутствуют** среди 881 definition — при этом дерево полное, и consumer работает без единой ошибки.
- Весь consumer-инструментарий читает только корни + `assetRefs` + previews; definitions не нужны ни для одной операции.

Следствие: массовый экспорт definitions — опциональный «справочный» слой, а не необходимый. Текущее поведение экспортера (limitations в `agent/index.md` это подтверждает): «per-definition IR cover selected and **reachable** definitions». Требуемое изменение — **переопределить reachable**: «инстанцирован в selected roots», а не «принадлежит сету, где инстанцирован хотя бы один вариант».

## 3. Ожидаемый контракт выгрузки

### 3.1 Обязательное ядро (не трогать)

- `ir/nodes/roots/*.json` — по одному на `scope.orderedRootIds`, с инлайненными инстансами как сейчас. **Не** заменять инлайн-поддеревья ссылками на definitions.
- `previews/<root-id>.png` — по одному на корень.
- Все файлы, на которые ссылаются `assetRefs[].archivePath` в деревьях корней, — физически присутствуют на диске (сейчас гарантия соблюдена: 8/8; сохранить).
- `manifest.json` + `diagnostics.json` + `agent/index.md`, `agent/tokens.md`, `agent/styles.md`, `ir/document.json`, `ir/styles.json`, `ir/variables.json` — маленькие, оставляются как есть (сводка counts должна честно отражать новый объём).
- Детерминизм порядка обхода (уже заявлен в limitations) — сохранить.

### 3.2 Component definitions — скоупировать до used-набора

Экспортировать только определения, **реально инстанцированные в selected roots** (в кейсе: 51 из 881). Если формат/схема допускает выгрузку вовсе без per-definition IR (ядро самодостаточно) — это тоже приемлемый результат; тогда в `components.json` достаточно index-записей по used-набору. Решение на усмотрение автора плагина с учётом требований формата figma-design-ir.

### 3.3 Остальные слои следуют тому же used-набору

- `assets/vector`, `assets/raster` — только файлы из `assetRefs` деревьев корней. Не экспортировать ассеты «достижимые через definitions и paint styles».
- `agent/components/*.md` + `component-index.md` — только по включённым definitions.
- `raw/rest-v1/` — корни всегда; `raw/rest-v1/components` — зеркало used-набора (или исключить слой целиком — допустимо).
- `agent/index.md` — **не инлайнить простыню diagnostic-ID** (сейчас 886 штук в тексте): достаточно ссылки на `diagnostics.json` и aggregates.

## 4. Алгоритм вычисления used-набора (проверен на кейсе)

1. Для каждого корня из `scope.orderedRootIds` взять JSON дерева.
2. Used defs = все `nodeId` определений, встречающиеся в тексте JSON как подстрока (надёжно: ссылки живут в нескольких полях — `source.id` инстансов вида `I<inst>;<comp>[;<sub>...]`, `componentPropertyReferences` вида `'Title content#107:15'`, `instanceData`). Эквивалентно: разложить id инстансов по сегментам `;` и взять числовые `<x:y>` сегменты.
3. Транзитивное замыкание: просканировать JSON включённых definitions на предмет ссылок на дальнейшие definition-id, повторять до фикспойнта (вложенные компоненты в компонентах).
4. Used assets = объединение `assetRefs[].archivePath` по деревьям корней.
5. Слои из §3.3 фильтровать строго по этим множествам. Ничего «на всякий случай» не добавлять.

## 5. Инварианты (ломать нельзя)

1. Самодостаточность `normalizedTree` — инстансы инлайнены, значения точные.
2. Каждый `archivePath` из `assetRefs` существует на диске; `contentSha256`/`byteLength` в `manifest.entries` соответствуют файлам.
3. Markdown-навигация (`agent/`) ссылается только на существующие файлы; канонический JSON приоритетнее markdown.
4. `scope.kind: current-selection` + `orderedRootIds` — семантика не меняется.
5. Схема figma-design-ir (сейчас 1.0.0) не ломается: это изменение скоупа, не формата. Если без bump версии не обойтись — задокументировать отдельно.
6. `coverage` в корневом IR — честный: если definitions скоупированы, статус `dependencies` отражает это без «collected» вранья; diagnostics после фикса должны резко сократиться (цель для кейса: ~0 по причинам «недоступная библиотечная definition»).

## 6. Критерии приёмки (тот же selection — попап `27053:15077`)

1. Объём архива: < 30 МБ и < 800 файлов (ориентир: core ≈ 12 МБ = корень 9.4 МБ + превью + 8 SVG + manifest/diagnostics).
2. `ir/components/definitions/`: ≤ ~60 файлов / < 10 МБ (или отсутствует — см. §3.2); в частности **ноль** определений флагов стран кроме `russia`/`portugal`, платёжных методов кроме `Mastercard sm`.
3. `assets/vector/`: ровно файлы из `assetRefs` (в кейсе 8); `agent/components/` — тот же count, что definitions; `component-index.md` — соответствующее число записей; в `agent/index.md` нет инлайн-списка diagnostic-ID.
4. Валидация consumer'ом (если доступен репозиторий madetask-frontoffice-react, ветка `release-with-claude-tools`):
   ```bash
   node .claude/skills/figma-to-code/scripts/figma-inspect.js figma-data/<scope> tree
   node .claude/skills/figma-to-code/scripts/figma-inspect.js figma-data/<scope> colors
   node .claude/skills/figma-to-code/scripts/figma-inspect.js figma-data/<scope> assets
   node .claude/skills/figma-to-code/scripts/figma-inspect.js figma-data/<scope> export-svg "<asset node-id>" /tmp/x.svg
   ```
   Все команды должны работать без ошибок и давать те же результаты, что на текущей выгрузке (скрипт читает только корни + assetRefs — это и есть регресс-тест самодостаточности).
5. Повторная выгрузка того же selection даёт побайтно-детерминированный набор путей (порядок и состав стабильны).

## 7. Свобода реализации

- Хранить ли per-definition IR вообще (§3.2) — на усмотрение по требованиям формата; consumer'у нужны только корни + previews + assetRefs.
- Способ фильтрации внутри плагина (не ходить в сеты вообще / ходить и фильтровать) — любой; критичен только результат.
- Если у формата есть другие consumer'ы, которым нужны полные сеты — сделать это opt-in флагом экспорта, по умолчанию used-набор.
